# 服务重载后的任务续跑

任务提交后先保存执行参数和参考图，再调度后台工作。启动时扫描未完成任务，此后每 15 秒补扫；上一个进程仍在处理的任务会在其释放执行锁后重新检查。

## 生图与换装

- `queued` / `preparing`：确认尚未发送付费生成请求（可能仍在排队或上传参考图），允许按原提示词、画质、变体、参考图继续提交。
- `submitting`：请求可能已经发送。没有可查询任务号或结果地址时，显示受理状态待核对，不自动重新生成。
- `accepted`：APIMart / APIMart Ext 沿用原任务号查询；FLUX 换装沿用返回的原轮询地址查询。
- `downloading`：只下载原结果；异步渠道的签名地址失效后重新查询原任务。
- `downloaded`：沿用已落盘的原图补齐结果记录。聊天结果按任务号去重。

Sub2API、Tuzi、Adobe2API 为同步响应接口，当前没有接入可用于恢复的任务查询接口。收到结果地址后可以继续下载；等待响应时重启且没有结果地址则只能提示核对，不能凭响应 ID 再次生成。读超时、发送后断连、提交阶段 HTTP 408 / 5xx 均不能证明上游没有受理，智能路由也会停止切换渠道。

查询或下载遇到临时故障时最多尝试恢复 3 次，始终沿用同一个本地任务和上游任务。智能路由中的明确终态失败会继续下一线路，仍遵循原定的两轮尝试；内容审核拒绝立即停止。恢复中的单个上游任务若明确失败则结束恢复。旧版已标记失败但保留了 APIMart 任务号的记录，会安全查询一次并按新机制处理，不重新提交。

图片落盘后，成功结果入库和聊天通知补写使用各自独立的计数，分别最多尝试 3 次，失败后等待 15 秒、30 秒再试。只读取已落盘的原图，不再查询或提交上游。

成功结果尚未入库时保持处理中；连续保存失败后标记任务失败和 `result_persistence_failed`，明确提示保存失败，保留原图及恢复地址，退出扫描。只有数据库中已保存成功结果及有效图片地址，才在聊天通知补写期间保留成功状态。通知补写连续失败后保存 `finalization_failed`，退出扫描，图片仍可查询和下载；补写成功则按任务号去重。检查点更新在同一条 SQL 中校验图片地址，避免产生无图片地址的成功任务。

## 合成与特殊品

普通合成复用已保存的 Penpot 工作副本。特殊品两种流程会持久化流程类型、工作副本、画板及版本导出计划；每张 PNG 完整写入后保存校验值。续跑只补缺失或校验失败的导出，按原计划切换版本。缺图不再标记为合成成功。历史查询和下载可直接从数据库恢复，不依赖进程内存。

旧版特殊品的普通版/完整版类型优先通过原进度日志识别。日志也缺失时，查询与下载兼容用户访问的原接口；该读操作不会补入执行用的类型字段。缺少执行流程信息的旧任务仍不自动续跑，而是明确提示重新合成。新提交的任务均包含类型记录。

## 部署

保持同一份 `jobs.db` 和输出目录。执行锁位于输出目录的 `.task-locks`，由操作系统在进程退出时释放；不要在进程仍运行时删除锁文件。普通请求与恢复请求使用相同的锁，特殊品导出还共享一个 Penpot 执行锁。

前端收到恢复状态后显示恢复提示，完成或明确失败后清除。恢复期间延长原任务的查询等待（最多 1 小时），避免前端先将仍在续跑的任务判为超时。网络断开时只重试原任务的状态查询，不重放生成 POST；会话过期后要求重新登录。

本机制覆盖普通生图、AI 换装、扩图、普通模板合成和两种特殊品合成。抠图、超分、矢量化、PSD 分层等独立任务暂未接入启动续跑。
